## 1. Findings

### H1. High: Redis is unencrypted and carries personal data plus a credential that can drive the DM engine
Verified: `vendor/openreply/lib/queue/client.ts:25-64` defines the job payloads. They contain `commentText`, `commenterId`, `commenterName`, `mediaId`, `instagramAccountId` (comment jobs), `userId` and `payload` (postback jobs), and `messageText`, `senderId` (inbound DM jobs). `defaultJobOptions` keeps the last 1000 completed jobs (`removeOnComplete: {count: 1000}`) and failed jobs for 5 minutes, so up to 1000 commenter name/ID/text records sit in Redis at any time. The retention purge (`packages/publisher/src/retention.ts`) only cleans Postgres, so Redis copies are outside the PII retention policy. `docs/MORNING-CHECKLIST.md:29` records that the connection is `redis://`; `scripts/check-redis.ts:50` and `set-redis.ts:57` knowingly continue over it.
Scenario: anyone on the network path between Vercel/Render/your laptop and the Redis host (public Wi-Fi at the laptop, a compromised hop, a malicious VPN) reads every job (commenter IDs, names, comment text, DMs people send to the account) and captures the `AUTH` password. With the password they can `ZADD`/`LPUSH` BullMQ jobs: a forged `ProcessCommentJob` with a trigger keyword makes the worker send real DMs (with the campaign link) to any Instagram user ID, as your account. That is spam from the production account (Meta policy strike, account restriction) and a way to spend your hourly DM budget. Interception is S (needs path access); the payload contents and the forgery capability are V.
Mitigations, in order of strength: (1) TLS: use `rediss://` (Upstash, Redis Cloud paid tiers, or a Redis behind stunnel/Caddy on the Oracle VM); (2) if TLS is truly unavailable, restrict the Redis ACL/source-IP allow-list to the fixed egress IPs of the Render/Oracle worker and never run `npm run dm-worker` from a roaming laptop; (3) use a Redis ACL user limited to `~bull:dm-processing:* +@all -@dangerous`; (4) lower `removeOnComplete` to ~50 or 1 hour so less personal data lingers; (5) rotate the Redis password every time it has crossed an untrusted network.

### M1. Medium: SMTP STARTTLS is opportunistic (V)
`alerts.ts:53-61` sets `secure: port === 465` and nothing else. In `node_modules/nodemailer/lib/smtp-connection/index.js:1341` the client sends STARTTLS only `if (!ignoreTLS && (server advertises STARTTLS || options.requireTLS))`. An attacker able to modify traffic between the host running the monitor (Vercel function, or the laptop via `test-email`) and `smtp-relay.brevo.com:587` removes the `250-STARTTLS` line; nodemailer then continues in plaintext and sends `AUTH` with the SMTP key and the alert body. Certificate validation is otherwise on by default (no `rejectUnauthorized: false` anywhere), so the fix is one line.
Fix: add `requireTLS: true` (and `tls: { minVersion: "TLSv1.2" }`) to the `createTransport` options in `alerts.ts`; keep `secure: true` for 465.

### M2. Medium: unbounded plaintext `.env` backups, readable by every local account (V)
`env-update.ts:44` copies the whole target file to `<file>.bak-<key>-<timestamp>` on every call. `set-env` calls it once per variable, so one multi-`--var` run made eight full copies (`.env.bak-alert_*`, `-monitor_token-`), and the directory now holds 10 root backups plus 4 under `vendor/openreply/`. Each is a complete copy of every secret (DB URL with password, Meta tokens, service-role key, encryption key, SMTP key), including superseded credentials (the old Redis and `DATABASE_URL` values) that should be dead but are still on disk. They are git-ignored (`.gitignore` has `.env.*`, V) so they cannot be committed, but they are not cleaned up and are not protected: `icacls D:\jqp` shows `NT AUTHORITY\Authenticated Users:(I)(M)` and `icacls D:\jqp\.env` shows `BUILTIN\Users:(I)(RX)`, i.e. the ACL inherited from `D:\` lets any local Windows account read the secrets and modify the tree. On a single-user laptop this is a hygiene problem; on a shared or family PC, or after any malware running as a different user, it is a full compromise.
Fix: take one backup per run (not per key), keep the latest 1-2, delete the rest; `icacls D:\jqp /inheritance:r /grant:r "%USERNAME%:(OI)(CI)F" "SYSTEM:(OI)(CI)F"` (or move the repo under `C:\Users\<you>`); delete the existing `.env.bak-*` files after confirming `.env` works, and rotate any credential that was superseded only because it leaked.

### M3. Medium (S): secrets typed on the command line
`set-env.ts:126` takes `--var KEY=VALUE`; `set-database-url.ts:290` and `set-redis.ts:193` take `--url`. A value passed this way is stored in PowerShell's PSReadLine history (`ConsoleHost_history.txt`, persisted across sessions), visible in the process list to other local users while it runs, and possibly in terminal transcripts or the Claude Code transcript. The backup names show `alert_smtp_host/port/user/pass`, `alert_email_*` and `monitor_token` all written by one run at 14:23:23; since the only value inputs of `set-env` are `--var`, `--copy` (from `.env`) and `--generate`, the SMTP key was either typed with `--var` (so it is in shell history) or the token was copied. I cannot see the history, hence S.
Fix: add a `--prompt KEY` mode that reads the value from a hidden prompt (or stdin) and make `--var` refuse names matching `/PASS|SECRET|TOKEN|KEY|URL/` unless `--insecure` is given. Immediate action: clear the matching lines from `%APPDATA%\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt` and rotate the Brevo SMTP key if it was typed.

### M4. Medium: MCP confirmation is advisory; ingest path unrestricted by default (V)
- `apps/mcp/src/index.ts:78` makes `confirm` a `z.literal(true)` argument that the *model* fills in. A prompt-injected or merely over-eager model can supply it, so the schema stops accidents, not attacks. The real gate is Claude Code's per-tool permission prompt; if the user ever chooses "always allow" for `mcp__jqp__publish_post` or `configure_campaign`, nothing human remains. `configure_campaign` accepts any `https://` `destinationUrl` and free-text DM copy, so with `enabled: true, confirm: true` on a published post, a bad instruction makes the account DM a phishing link to every commenter. Note `.claude/settings.local.json` currently lists `jqp` under `disabledMcpjsonServers`, which is the safe state.
- `index.ts:248-253`: the `POSTS_ROOT` check runs only when the variable is set. `POSTS_ROOT` is not in `.env.example` or `packages/core/src/env.ts` (grep: only the MCP file and docs), so by default `ingest_post_folder` accepts any readable directory, and the local worker later uploads images from it to the *public* Supabase bucket. The check also does not `realpath` (symlink escape) and compares case-sensitively on Windows (fails closed, but only by accident).
- `apps/web/app/api/posts/route.ts:24` passes `folderPath` straight to `ingestPostFolder` with no restriction at all: audit 1 finding 6 is **still open**.
Fix: enforce the root inside `ingestPostFolder` (single choke point for web, MCP, worker) using `fs.realpath`; make `POSTS_ROOT` required in production; document that MCP publish/enable tools must stay on "ask every time"; optionally require a short human-typed code echoed by the dashboard for live-DM enablement.

### M5. Medium: Postgres connections do not verify the server certificate (V)
`packages/core/src/db.ts:20` uses `ssl: "require"`. In postgres.js, `require` is TLS *without* validation: `node_modules/postgres/src/connection.js:284` sets `options.rejectUnauthorized = false` for it, and only `verify-full` or an explicit CA validates (`index.js:445`). `scripts/set-database-url.ts:328` has the same setting. An active MITM between the app and the Supabase pooler (most realistic for the laptop-hosted worker and any `npm run` script on untrusted Wi-Fi) can present any certificate and read or alter all queries, including `DATABASE_URL` credentials and every row of PII.
Fix: pass `ssl: { ca: <Supabase root CA PEM>, rejectUnauthorized: true }` (Supabase publishes its CA) or `ssl: "verify-full"` with `sslrootcert`; apply to `set-database-url` as well.

### M6. Medium: `scrubText` / `scrubMeta` miss many secrets and personal values (V, tested)
Run against adversarial strings (`events.ts:267-287`):
- Not redacted: `token=EAAB1234567890abcdef1234567890` (30 chars), `password=hunter2`, a 22-character Redis password in prose, an AWS secret key containing `/` (split below 32 chars), a JWT is only partly redacted (`eyJhbGciOiJIUzI1NiJ9.[redacted].[redacted]` keeps the header), `AKIA...` access key IDs, host names such as `db.<ref>.supabase.co`, the Postgres role `postgres.<ref>` inside "password authentication failed for user ...".
- Personal data passes through unchanged: `john.doe@example.com`, `@some_user`, `+91 98765 43210`, numeric Instagram user IDs, and any name in free text. In `scrubMeta`, only the *key name* is tested (`DROP_META_KEYS`), so `{reason: "john@example.com said hi"}` and `{note: "Bob Smith wrote: call me"}` are stored verbatim.
- The rule is "nothing personal goes in `system_events`" (CLAUDE.md, migration 0008 header). Event messages include raw Meta error text (`pipeline.ts:100,108`, `apps/worker/src/index.ts` `publish_rate_limited`), raw 5xx exception text (`api-error.ts:31`, `message` argument) and `DmLog.errorMessage` (`system.ts:231`); Meta/driver errors do sometimes echo usernames, IDs, row values (`Key (ig_user_id)=(...)`) or SQL parameters.
- Alert emails are safer than the event log: their subject/body are built only from fixed labels and fixed `detail` strings in `system.ts` (V), so a secret in `system_events` does not reach email today.
Fix: add redaction for `[\w.+-]+@[\w-]+\.[\w.]+`, `@[A-Za-z0-9._]{2,}`, `\+?\d[\d\s().-]{8,}\d`, `(token|password|secret|key|pass)\s*[=:]\s*\S+`, base64/hex runs of 20+ including `/+=.`, and the `postgres.<ref>` pattern; for `scrubMeta`, run values through the same patterns (already done) and add the email/handle ones; in `apiError`, record only the error *class* and the `event` code, not `err.message`, for 5xx.

### M7. Medium: vendored OpenReply cron auth and public health (carried, V in code)
`vendor/openreply/app/api/cron/*/route.ts:9-12` still does `authHeader !== \`Bearer ${CRON_SECRET || NEXTAUTH_SECRET}\``: non-constant-time, falls back to the NextAuth secret (so one secret guards sessions and cron), and if both env vars are unset it accepts `Authorization: Bearer undefined`. `/api/health` still returns raw `error.message` for the DB, Redis and queue checks plus queue counts and worker heartbeat to anyone (`health/route.ts:21-90`). The vendor tree is unmodified since audit 1 (`git diff 2f21708..HEAD --stat -- vendor` is empty) as required. New aspect: `system.ts:77-90` now *depends* on this public endpoint, and it is an unauthenticated route that costs one DB query, one Redis ping and a queue-count call per hit (cost/DoS amplification, and a hung Redis hangs the request).
Fix without touching vendor: set `OPENREPLY_CRON_SECRET` to a long random value distinct from `NEXTAUTH_SECRET` (the .env.example has the slot, line 250); put a Vercel firewall/rate rule or a rewrite in front of `/api/health` on the OpenReply project that only allows the monitor's requests (or add a secret header the bridge checks); confirm both env vars are set in production.

### L2. Low: `/api/cron/*` behaviour with a valid or leaked token (V)
The guard itself is sound (I1). Residual: (a) no rate limit; a leaked `MONITOR_TOKEN` lets a caller trigger the monitor (OpenReply fetch, ~8 DB queries, `alert_state` writes) and the purge as often as they like, which is cost and DB-pool pressure but not data exposure; email volume stays bounded by the alert-state machine. (b) Two overlapping runs (a scheduled run plus `workflow_dispatch`, or a retry) both read `alert_state` before either writes and both email the same "newly failing" check; there is no `select ... for update` or `insert ... on conflict do nothing returning`. (c) `alerts.ts:210-212` rethrows persist errors other than "table missing"; the route returns 500 and the next run sees the check as newly failing again, so a persistently failing write produces an email and an event every 10 minutes.
Fix: do the state transition in one SQL statement (`update alert_state ... where status <> excluded.status returning`) and email only for rows it returned; catch persist errors, log them and return 200 with a flag; cap the monitor with a Vercel firewall rate rule.

### L3. Low: `env-update` robustness (V)
`updateVercel` runs `vercel env rm` then `env add` (`env-update.ts:69-70`). If the `add` fails (network, plan limit, CLI auth expiry), production is left without `DATABASE_URL` or `REDIS_URL` until someone notices: the script reports the failure but the live variable is already gone. `updateLocalFiles` writes `KEY=value` raw: a value containing a newline, ` #` or quotes silently truncates or injects extra variables (`line` is built at line 47), and `new RegExp(\`^${f.key}=.*$\`)` interprets the key as a regex (self-inflicted only, the key comes from the operator). With `shell: true` on Windows (line 63) the `--vercel` project name goes through `cmd.exe` (self-inflicted only). The temp directory is `mkdtemp` under `%TEMP%` (random name, per-user), not world-writable.
Fix: `vercel env add` first to a temporary name, or `env update` if available; reject values with `\n`, `\r`; quote values that contain `#` or spaces; validate key names with `/^[A-Z][A-Z0-9_]*$/`.

### L4. Low: GitHub Actions workflow (`.github/workflows/monitor.yml`)
Good: `permissions: {}`, no third-party actions, no `${{ }}` interpolation of untrusted input inside `run:` (the `github.event.schedule` value is only used in `if:`), secret passed through `env` and quoted `$MONITOR_TOKEN` in the shell, `timeout-minutes: 3`, `-m` limits. Residual: (a) `curl --fail-with-body -sS` prints the JSON response into the Actions log (`{checked, failing:[check keys], newlyFailing, emailSkippedReason}`), which is world-readable if the repository is public (visibility could not be determined here: `gh` is not installed; remote is `git@github.com:reesick/jqp.git`); (b) `MONITOR_URL` is a plain variable with no `https://` check, so a typo with `http://` sends the bearer token in clear; (c) on a public repo, GitHub disables scheduled workflows after 60 days with no repository activity, which silently stops monitoring and retention purge (the file's own comment says this); (d) anyone with write access can run `workflow_dispatch` and so trigger purge. 
Fix: `curl -sS -o /dev/null -w "%{http_code}\n" --fail` (do not echo the body), add `case "$MONITOR_URL" in https://*) ;; *) exit 1;; esac`, keep the repo private or add a keep-alive, and use a second independent heartbeat (UptimeRobot on `/api/health`).

### L5. Low: `normalizeMessageText` data corruption (V, no DoS)
ReDoS/DoS: none found. Input is capped at 5000 characters; 12 adversarial 5000-character inputs (runs of `*`, `_`, `` ` ``, `[`, `-`, `\`, newlines, spaces, unterminated link) all finished in under 35 ms (I3). Corruption: (a) `message-text.ts:378` turns any literal `\n`, `\r`, `\t` into whitespace, so `C:\new\table` becomes a line break plus `ew`/tab plus `able`, and any DM copy that deliberately contains a backslash sequence is mangled; (b) line 403 rewrites ` -- ` between spaces to an en dash, so `rm -rf -- ./dir` becomes `rm -rf – ./dir`; (c) `*real emphasis*` and `_x_` are stripped by design but also `5*3*2` is preserved while `a *b* c` loses its asterisks, which can change meaning in a price formula. It is by-design formatting removal, so Low, but `preview_dm` and the dashboard should show the cleaned diff (the MCP does). Throwing on >5000 chars is correct and surfaces as an error rather than truncation.

### L6. Low (S): MCP returns externally-derived text to the model
`get_post` returns `caption`, `error_message`, `sync_error`; `recent_problems` returns event `message`s and failed-post errors; `system_health` returns `topFailures[].reason` (from `DmLog.errorMessage`, scrubbed only by M6's weak `scrubText`). Error text originates in Meta/Postgres responses and could, in principle, carry attacker-influenced strings (for example a comment text echoed in a Meta error), which becomes prompt-injection input to an agent that also holds `publish_post` and `configure_campaign` (see M4). No commenter names or comment text are returned directly (`recent_problems` description is accurate), and the server loads the root `.env` into its own process but never returns it (V: `safe()` strips `postgres://` from errors; results are projections of rows, not env). Fix: keep M4's "ask every time" rule, prefix such fields with an explicit "untrusted data" marker, and cap lengths.

### L7. Low: still open from audit 1
See section 2: findings 10 (health runs a DB query per hit), 11 (AES-GCM tag length not pinned, `crypto.ts:32-37`), 13 (Meta token in query string, `client.ts:79`), 14 (logger redaction lacks `key`/`databaseurl`/`dsn`, `logger.ts:25-37`), 15 (Supabase project ref and pooler host in docs), 16 (`NODE_ENV` defaults to `development`, `env.ts:16`). Also no `Strict-Transport-Security` or `Content-Security-Policy` in `next.config.ts:15-24` (Vercel adds HSTS on `*.vercel.app`, not on a custom domain).

### L8. Low: residue from the helper scripts
`%TEMP%\jqp-env-*` holds 10 leftover directories (the comment at `env-update.ts:75` anticipates it): each contains a `.vercel/project.json` (project and org IDs), no secret values, since values go to `vercel env add` on stdin (V, good). `readClipboard()` and `set-env --generate/--clipboard` move secrets through the Windows clipboard; with Clipboard history (Win+V) or cloud sync enabled they persist or sync to other devices. Fix: delete the directories on exit with `fs.rmSync` after the child process closes (retry), and clear the clipboard after use (`Set-Clipboard -Value $null`).

### Informational (verified good)
- **I1** `/api/cron/*` guard (`cron-auth.ts:14-29`): fails closed (503) when `MONITOR_TOKEN` is unset, malformed, or shorter than 24 characters; compares with the shared constant-time function (length is compared first, which leaks only length); 401 on any mismatch, before any DB or email work; POST only; the middleware bypass (`middleware.ts:25`) is documented with a warning and both existing routes call the guard first. Anyone reaching it without the token costs one `loadEnv()` parse.
- **I2** Email header injection: tested with `nodemailer` stream transport: a `\r\nBcc: evil@x.com` in the subject came out as `Subject: [DOWN] jqp: Evil Bcc: evil@x.com` (folded into one header, no new header). Anyway subjects use fixed labels only. `from`/`to` come from env.
- **I3** Normaliser is linear/bounded, see L5.
- **I4** Meta rate-limit handling (`client.ts:80-100`, `errors.ts`, `usage.ts`, `jobs.ts:63-70`): inline retries are bounded (max 3 attempts, waits 1-8 s or the Meta hint but never over 20 s), longer hints are handed to the queue, queue retries are `retryLimit: 8` with exponential back-off (about 4 hours), then the job ends. `Retry-After`/usage parsing is NaN- and negative-safe (`num()` and `Number.isFinite`), invalid JSON headers are ignored, the usage observer is throttled to 10 minutes and its exceptions swallowed. No infinite loop or amplification found. Minor: 5xx and 429 are all `RateLimitError`; the queue ignores the hinted delay and uses its own schedule, which is fine.
- **I5** Secrets in git: `git ls-files` (360 files excluding the lockfile) grepped for AWS (`AKIA`), Brevo (`xsmtpsib-`, `xkeysib-`), JWT (`eyJ...`), Instagram (`IGAA`, `EAA`), Resend, `sk-`, private-key headers, `postgres://user:pass@`, `rediss://default:...@`: no real credentials. Matches were fake test fixtures (`postgresql://user:pass@localhost` in four test files, `IGAA...` strings in `events.test.ts:13`, a 64-hex test cipher key in `vendor/openreply/.github/workflows/ci.yml:49`, JWT-shaped cookies in `smoke-test.ts:94`/`edge-safe.test.ts:31` that are deliberately invalid). `git log --all --diff-filter=A --name-only` shows no `.env`, `.pem`, `.key` or backup file ever added (only `.env.example`, `scripts/*env*`, `lib/env.ts`). `.gitignore` has `.env` and `.env.*` (except `.env.example`), which covers `.env.bak-*` in both the root and `vendor/openreply/` (V by pattern; I deliberately did not run `git check-ignore` on those file names).
