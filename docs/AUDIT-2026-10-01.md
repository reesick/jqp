# Audit summary, 2026-10-01

Two independent auditors reviewed the system without having written any of it. This page is the short version and the action list. Details: `docs/SECURITY-AUDIT-2.md` (security) and `docs/COMPLIANCE-AUDIT-2.md` (Meta compliance, data protection, scale). Earlier rounds: `docs/SECURITY-AUDIT.md`, `docs/DATA-PROTECTION.md`.

## Audit plan that was followed

1. **Scope:** everything added since the first audit (monitoring, cron endpoints, SMTP alerts, the Claude Code server, helper scripts, rate-limit handling), plus a re-check of every earlier finding.
2. **Method:** read-only review by fresh agents with no stake in the code; no live services touched; secrets never read. Findings tagged verified (read in code or reproduced) or suspected.
3. **Questions asked:** can an outsider reach or abuse anything? Can secrets or personal data leak? Does behaviour meet Meta's rules? What happens in a viral burst? What breaks when the owner is away?
4. **Output:** severity-ranked findings with a minimal fix each.

## Verdicts

- **Security:** 0 critical, 1 high, 7 medium, 8 low. No regressions against the first audit. The earlier fixes (session tokens, headers, cron guard, event scrubbing, message cleaning) hold.
- **Compliance and operations:** the code is careful, but the system is **not yet fit to run unattended at 500 to 1000 DMs a day**, mostly because the safety nets are switched off and a few copy and pacing choices carry spam-report risk. Fixable with configuration and small changes.

## Open, in priority order

### Do before relying on this while you are away
1. **Switch the safety nets on.** The GitHub workflow that runs the health monitor and the cloud retention purge does nothing until the repo secret `MONITOR_TOKEN` and variable `MONITOR_URL` are set (`npm run set-env -- --clipboard MONITOR_TOKEN` copies the token). Until then no alert email can fire and retention only runs when the laptop worker is up.
2. **Rotate credentials that appeared in chat:** Supabase database password, Redis password, Brevo SMTP key. Also clear the matching lines from your PowerShell history (`%APPDATA%\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt`).
3. **Delete the `.env.*bak*` backup files** in the repo folder and in `vendor/openreply/` once you have confirmed everything works. They are full plaintext copies of your secrets, and the repo folder is readable by other local Windows accounts (`icacls D:\jqp` shows `Authenticated Users` with modify access). Tighten it: `icacls D:\jqp /inheritance:r /grant:r "%USERNAME%:(OI)(CI)F" "SYSTEM:(OI)(CI)F"`.
4. **First live campaign sends a direct DM with no "this is automated" line.** Meta's messaging policy expects disclosure at the start of an automated conversation. Add a disclosure line, or turn on the two-step opening message.
5. **Do not run the DM worker from a roaming laptop on public networks** while Redis is unencrypted. Anyone on the network path could read queued comments and, with the password, queue forged DMs from your account. You decided to leave Redis as it is for now; the cheapest improvements are a Redis plan or host with TLS later, or restricting the Redis source IPs to the worker's fixed address.

### Before scaling to hundreds of DMs a day
6. **Viral-burst pacing.** In a burst of 1000 comments, OpenReply sends about 750 DMs in roughly 4 to 8 minutes (cap 750 per hour, 5 at a time, no spacing), and posts public replies without pacing, all with the same text. Meta publishes no "safe" rate, so this is a judgment from the mechanics: it looks like spam. The fix is a lower hourly cap, a 20 to 40 second gap with jitter, reply variations, and a longer requeue budget. The auditor wrote the exact patch outline in `docs/COMPLIANCE-AUDIT-2.md` section (d); it edits vendored code, so it needs your approval. Button-tap reveal DMs and follow-ups bypass the cap, so they stay prompt.
7. **No per-person erasure path** and the data-deletion page names no contact (Meta's terms expect one). No STOP/opt-out handling.
8. **Redis keeps the last 1000 completed jobs** (commenter names and text) outside the retention purge.
9. **Publishing token** has no refresh job and expires in 60 days.
10. **Supabase backups:** the free plan has no automatic backups (plan unverified).
11. **Database TLS is not certificate-verified** (`ssl: "require"`), and the database role is a superuser.
12. **Claude Code server:** the `confirm: true` flag is filled in by the model, so it prevents accidents, not attacks. The real gate is Claude Code's own per-tool approval prompt. Do not choose "always allow" for `publish_post` or `configure_campaign`.
